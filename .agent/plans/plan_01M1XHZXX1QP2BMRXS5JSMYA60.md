# Implement authenticated rollover and distinct-suite migration


This living ExecPlan follows `.agent/PLANS.md`. Its consumer is the J18 implementer and the maintainer requesting the change. It gates J18 because inspection found an absent runtime, an undefined destination suite, and a circular witnessed-bootstrap commitment. Delete it after J18 acceptance and the requested commit review. It supplies no capability or security assurance by itself.

## Purpose


An owner must be able to create a fresh vault from all current active source state, including governed items, even when the source history is full. The source remains byte-for-byte intact. The new vault requires explicit trust, backup and redistribution. A second command must perform the same complete operation while changing to a distinct, accepted cryptographic suite. Neither command may silently omit an item or bypass witnessed authorization. Jury remains experimental and unsuitable for real secrets.

## Surprises & Discoveries


J18 is standalone follow-up work after Linux 0.0.1, outside release epic jury-qv4. Epic-scoped ready tasks are empty; J18 itself has four closed prerequisites and was open before this task claimed it. J26 and deferred J24 must not be reactivated by this work.

`SignedRolloverV1` and `SignedSuiteMigrationV1` already have frozen signing preimages in `crates/jury-protocol/src/vault_v1/preimage.rs`. `validate_source_attestation` checks rollover shape only; replay currently verifies the genesis owner signature but not the source-owner bridge or bootstrap manifest. There is no runtime rollover command.

The master plan's instruction to omit signatures and genesis fingerprint from the bootstrap manifest is insufficient for witnessed slots: `build_witnessed_slot` embeds genesis fingerprint and witness policy digest in HPKE info/AAD, so encrypted capsule bytes still depend on that fingerprint. Genesis itself contains the manifest commitment. A manifest committing final capsule bytes there would require a cryptographic fixed point. Existing direct slots and item ciphertexts do not have that dependency.

## Decision Log


Preserve the full combined J18 objective. Current-suite rollover is a milestone, never grounds to close J18. Do not introduce a second provider of suite 1 and call it migration. No new primitive/provider runtime implementation is authorized by a green suite-1 gate alone.

Resolve the bootstrap cycle in two phases while keeping existing capsule context binding intact. The pre-genesis manifest commits public bootstrap intent, fresh item/seal IDs and encrypted descriptor/body metadata that can be prepared without genesis. Its witnessed-policy projection includes complete membership, keys, quorums, rules and fresh IDs but excludes fields derived from genesis. Once genesis exists, create the bound witness policies and capsules; the source owner's signed first policy revision authenticates the complete resulting objects. Verification must compare the reconstructed intent with the genesis commitment and verify that first revision, including every capsule and resulting policy state. Final capsule bytes must never be treated as pre-genesis inputs. Specify the projection byte-exactly before implementation; if this cannot preserve every requested commitment, use an explicit versioned completion attestation rather than relaxing authentication.

Suite 2 candidate for evaluation is X-Wing/HKDF-SHA256 with HPKE AES-256-GCM (AEAD ID 2), retaining AES-256-GCM-SIV storage and Ed25519 signatures. It changes the cryptographic suite rather than merely its provider, retains storage misuse resistance and existing key dimensions, and makes no stronger retained-copy/security claim. This is a candidate, not accepted cryptography; compare its requirements with the suite-1 property matrix and validate exact provider support, public specifications and cross-implementation vectors before selection. The primary HPKE AEAD registry is RFC 9180 section 7.3.

## Idempotence and recovery


The source remains immutable. Absent-destination publication must never overwrite an occupied target. Any recovery record is a minimal integrity control preventing mismatched partial topology/publication from appearing ready; it binds exact source revision, destination ID, manifest and published outputs and is removed only after durable completion. Retries refuse mismatched source/candidate/output and stale authorization. On terminal failure leave source usable and describe partial destination/witness state accurately; do not silently discard external registrations or claim rollback succeeded. Private plaintext and keys stay in protected memory and never enter recovery files, output, receipts or test diagnostics.
