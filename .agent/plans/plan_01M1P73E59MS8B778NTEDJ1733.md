# Contain J17 recovery and publication invariants

This plan fixes `jury-qv4.2.15`, the concrete comprehensive-review follow-up to
J17. Its consumers are the native backup/restore CLI and the J25 adversarial
corpus. The observed defect classes are incomplete owner-slot construction,
cross-crate capacity drift, source-custody escape during drills, incompatible
persisted receipt evolution, and filesystem decisions made from different
object identities. Close this plan after every regression test and required
repository gate passes. Retain only this required plan and append-only Jig
receipts.

## Surprises & Discoveries

- The current normative plan requires direct or mixed items to carry access paths
  for every owner. The reviewed backup check is therefore correct to reject a
  missing owner slot; the defect is earlier, where item construction relies on
  callers to enumerate implicit owners.
- Backup reads are intentionally optimistic and core validation fails closed on
  mixed generations. A short state lock should make the three-file snapshot
  consistent, but the lock must not survive prompts or Argon2 work.
- The frozen receipt entry width can remain unchanged while a compatibility DTO
  selects the legacy payload digest or the current coverage digest for MAC
  verification.
- The protected-memory crate's ordinary 16 MiB ceiling remains appropriate for
  normal secrets, but the backup format declares authenticated 32 and 64 MiB
  buckets. A format-owned ceiling is necessary so raising backup capacity does
  not broaden every protected allocation.
- A retained `.jury` directory handle remains safe to access but no longer
  proves that the worktree name resolves to that directory. Retaining the
  identity and reopening under the retained worktree makes namespace continuity
  explicit.
- The first plan-aware gate run passed tests, formatting, clippy, and contract,
  but correctly rejected five changed modules whose responsibilities had grown
  beyond the repository LOC limits. The hard limit for changed files is 800
  lines even though 1,000 is the absolute maximum.

## Decision Log

- Derive implicit direct owner recipients inside `jury-core` whenever an item has
  a direct path, and validate complete owner slots at policy replay. Do not make
  backup silently reinterpret an invalid vault as partial coverage.
- Add an explicitly bounded protected-memory allocation/open path whose caller
  supplies the format ceiling, under one absolute protected-memory maximum.
- Carry the source home into the restore transaction as an exclusion capability;
  validate all targets centrally and pass both source and target repositories to
  hardened state-root checks.
- Separate legacy receipt wire decoding from the current runtime receipt model.
  Preserve old JSON and old MAC verification, and expose legacy coverage as
  unknown rather than fabricating new metadata.
- Store the metadata needed for visibility decisions in the retained file
  snapshot. Store only `.jury` directory identity and reopen it by name before
  each use.
- Separate archive codec/error translation, recovered-identity behavior, item
  sealing, backup argument schema, restore orchestration, restore publication,
  and restore transaction data. Keep the gate unchanged and validate the moved
  code with the same tests.

## Context and orientation

`crates/jury-core/src/item.rs` resolves item access and creates slots;
`policy/replay/operations.rs` validates replayed policy state. `backup.rs` owns
archive creation/opening and recovery coverage. `jury-protected` owns protected
allocation limits, while `jury-core/src/crypto.rs` owns authenticated open.
`backup_commands.rs` owns CLI target selection and local-state snapshot timing.
`local_state/receipts.rs` owns the authenticated persisted receipt schema.
`jury-filesystem` owns no-follow capabilities, destination snapshots, and Git
worktree publication.

## Plan of work

1. Make core access resolution union every active owner into a non-empty direct
   recipient set, adjusted for owner grant/revoke/replacement, and add a replay
   invariant requiring both current content-role slots for each direct owner.
2. Read audit, checkpoint, and receipt bytes under one short principal-state
   lock, releasing it before secret prompts and encryption.
3. Let format owners request a protected allocation with an explicit ceiling up
   to one absolute maximum; use the backup protocol ceiling on seal and open.
4. Validate drill source exclusion for vault, state, owner, approver, and witness
   targets, including repository capabilities rather than lexical paths alone.
5. Add a legacy backup-receipt wire DTO and MAC path while keeping the fixed
   receipt entry and current coverage commitment unchanged.
6. Make file mode/UID part of the same snapshot whose identity is checked at
   publication. Reopen `.jury` under the retained worktree and compare identity
   before every read, prepare, publish, or metadata write.

## Idempotence and recovery

All implementation steps are ordinary source changes and commits. Failed tests
leave no product state. Restore regression tests use temporary generic fixtures.
Do not delete or overwrite user files. If a partial commit exposes a compile
failure, repair only within that logical slice before committing it.

## Interfaces and dependencies

No new dependency is expected. Jury must remain independent of Jig at runtime.
Do not alter the frozen cryptographic suite or fixed receipt entry layout. Keep
all errors, fixtures, plans, and test output free of secrets and private names.
